# ADR-0001 · 采用模块化单体

- 状态：已采纳
- 日期：2026-11-27

## 背景

项目要同时展示四个限界上下文（Sales、Inventory、Billing、Fulfillment）、事务性 Outbox、Saga 补偿、CQRS 读模型与一个独立的事件溯源示例。目标读者是学习 DDD 的开发者，不是需要独立扩容的生产团队。

如果把每个上下文拆成微服务，会立刻引入：服务发现、网络调用、分布式事务/补偿的基础设施、跨服务测试、部署编排、可观测性等。这些是分布式系统问题，不是 DDD 教学重点，而且会让「一个命令跑起来」的目标失败。

## 决定

采用**模块化单体**：

- 单个 Maven 模块、单个 Spring Boot 进程、单个 H2 数据库；
- 顶层包按限界上下文划分：`sales`、`inventory`、`billing`、`fulfillment`；
- 跨上下文通过应用服务端口（`fulfillment/application/port`）与集成事件（`sharedkernel/outbox`）协作；
- 不共享领域对象，不跨上下文直接访问 `domain`；
- 用 ArchUnit（`ArchitectureTest`）守护边界，而不是靠网络隔离；`bootstrap` 是唯一允许直接装配各上下文领域对象的组合根。

## 后果

### 好的

- **一条命令即可运行**：`./mvnw spring-boot:run -Dspring-boot.run.profiles=demo` 能在几秒内看到完整时间线。
- **测试快且确定**：`@SpringBootTest` + H2 即可验证跨上下文 Saga，不需要容器编排或服务 stub。
- **边界仍然清晰**：包结构、端口、集成事件和架构测试共同约束依赖方向；读者能在一个仓库里对照四个上下文。
- **重构成本低**：修改 Sales 内部模型不会触发跨服务发布流程，只要集成事件契约不变。
- **教学信号强**：所有协作都在眼前，读者可以顺着一行调用看到另一个上下文，而不是跳转到远程仓库。

### 坏的

- **不能独立部署/扩容**：四个上下文共享进程与数据库，一个上下文的重负载会影响其他上下文。
- **故障不隔离**：Billing 的异常可能拖慢整个进程；没有服务级熔断、限流、重试策略。
- **数据库是共享的**：虽然代码按上下文分包，但所有表在同一个 H2 库中；没有物理 schema 隔离，误查其他上下文表在技术上可行。
- **架构约束靠测试与纪律**：`ArchitectureTest` 能阻止跨上下文依赖 `domain`，但无法验证运行时契约、SQL 或集成事件载荷；这些仍需代码评审与契约测试。
- **未来拆分有成本**：拆分微服务时需要把进程内事件换成消息中间件、端口换成远程调用，并处理分布式事务与数据迁移。

## 替代方案

| 方案 | 为什么不采用 |
|---|---|
| 微服务 | 引入网络、部署、分布式一致性等与 DDD 教学无关的复杂度；无法一条命令跑通 |
| 单层 monolith（按 controller/service/dao 分包） | 无法展示限界上下文与上下文映射；领域模型会与框架、SQL 混在一起 |
| Maven 多模块 | 能提供编译期边界，但增加构建与依赖管理复杂度；对本教学项目收益有限。包结构 + ArchUnit 已足够 |
| 模块化单体 + 独立 schema | 更接近生产，但需要额外的 schema 管理与跨 schema 查询配置；本项目优先保持运行简单 |

如果未来要演进，建议顺序是：先加 ArchUnit/模块边界，再按上下文拆分数据库 schema，最后才考虑把高负载上下文拆成独立服务。不要在边界尚未稳定时先拆服务。
