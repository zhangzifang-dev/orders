# ADR-0003 · 把 Money 放进共享内核

- 状态：已采纳
- 日期：2026-11-27

## 背景

Sales 需要计算订单总额、折扣与应付金额；Billing 需要开票金额与支付金额；Fulfillment 需要在跨上下文调用时传递应付金额。如果每个上下文各自实现一套金额类型，会出现：

- 舍入规则不一致（例如一处 HALF_UP，一处 HALF_EVEN）；
- 币种校验缺失，跨币种金额被静默相加；
- 同一个 API 在不同上下文中金额的小数位不同；
- 上下文之间传金额时反复转换，容易丢失精度或单位。

另一方面，共享内核的代价是真实的：多个上下文被同一份代码绑在一起，任何修改都需要协调升级。这不只是「多一个依赖」，而是**发布节奏与变更影响的耦合**。

## 决定

把以下类型放入 `com.example.orders.sharedkernel`：

- `Money`：`BigDecimal amount`（scale 2，`RoundingMode.HALF_UP`）+ `Currency`，不可变，跨币种运算抛 `DomainException`；
- `Currency`：ISO 4217 三位大写代码，当前演示只提供 `CNY`，但类型不写死；
- `Sku`：库存单位标识，去空格、转大写、非空；
- `Quantity`：1..999 的数量值对象；
- `OrderId`、`CustomerId`：跨上下文共享的标识值对象；
- `AggregateRoot`、`DomainEvent`、`DomainException`：极薄基类/接口，不含框架依赖。

集成事件位于 `sharedkernel/outbox`，作为**发布语言**模块；它依赖 `Money`、`Currency`、`OrderId` 等共享类型，但不依赖任何业务上下文。

## 后果

### 好的

- **金额语义一致**：所有上下文对「元、两位小数、HALF_UP、币种不匹配即报错」有同一理解。
- **跨上下文契约直接可用**：`OrderPlacedIntegrationEvent` 可以直接携带 `Money`、`Currency`，Fulfillment 无需再做单位换算。
- **值对象测试一次覆盖多处**：`MoneyTest` 的舍入、跨币种、负零等测试保护了 Sales、Billing、Fulfillment。
- **减少重复代码**：不需要在四个上下文各写一套 `Money` 与 `Currency`。
- **标识一致**：`OrderId` 在四个上下文中含义一致，避免了「Sales 的 orderId 是 UUID、Billing 的是 String」这类转换错误。

### 坏的（耦合代价）

- **变更需要全局协调**：修改 `Money` 的 API（例如把 `multiply(int)` 改成 `multiply(BigDecimal)`）会影响所有上下文。即使某个上下文不需要新行为，也必须一起升级、重跑测试。
- **发布节奏被绑定**：共享内核没有独立版本；四个上下文只能随同一个应用一起发布。若拆成微服务，需要把共享内核抽成带语义化版本的库，并处理多版本共存。
- **容易膨胀成「大泥球」**：一旦允许把 `OrderStatus`、`InvoiceStatus`、`FulfillmentStatus` 也放进共享内核，它就会变成跨上下文的领域模型，边界名存实亡。本项目刻意不这么做。
- **隐性契约**：共享内核的字段/方法会被所有上下文看到，读者可能误以为可以跨上下文共享更多东西。
- **测试耦合**：共享内核的测试失败会阻塞所有上下文的构建；需要更严格的兼容性纪律。
- **领域纯度被妥协**：`AggregateRoot.version/assignVersion` 是持久化关注点，却放在共享内核基类中。这是有意的务实妥协，用于支持 Spring Data JDBC 乐观锁；它不参与业务不变量，但确实让领域基类知道「版本」这件事。

**结论：共享内核只放真正稳定、且多个上下文必须保持一致的值类型。** 一旦某个类型开始承载业务规则或频繁变化，就应移出共享内核，改用上下文内模型 + 防腐层/集成事件翻译。

## 替代方案

| 方案 | 为什么不采用 |
|---|---|
| 每个上下文复制一份 `Money`，边界处转换 | 边界清晰，但四份实现容易漂移；舍入/币种规则不一致会产生真实金额错误 |
| 独立 `money` 库（带版本） | 适合微服务/多团队，但本教学项目是单模块单体，增加版本管理成本而收益有限 |
| 只通过集成事件传字符串金额，各上下文自行解析 | 契约简单，但把解析与校验责任推给每个消费者，容易漏掉币种与精度 |
| 把金额建模为 `long` 分 | 避免小数问题，但业务人员读代码时不直观；本项目选择 `BigDecimal` + 明确 scale，便于教学 |
| 让 Billing 拥有金额类型，Sales 通过 ACL 转换 | 耦合方向反了：核心域 Sales 不应依赖支撑域 Billing 的模型 |

如果未来拆服务，建议把 `sharedkernel` 中的值对象抽成独立、语义化版本的 `money`/`identifiers` 库，并在集成事件 schema 中固定金额的序列化格式（如字符串 + 币种），而不是直接序列化 Java 类型。
