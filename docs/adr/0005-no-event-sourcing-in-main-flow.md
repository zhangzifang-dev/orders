# ADR-0005 · 主流程不采用事件溯源

- 状态：已采纳
- 日期：2026-11-27

## 背景

本项目的主流程（Sales / Inventory / Billing / Fulfillment）需要在教学代码里同时表达：

- 订单、库存、发票、支付、履约流程的当前状态；
- 聚合不变量与状态机；
- 跨上下文 Saga 与补偿；
- CQRS 读模型。

有两种更「事件化」的方案可以做到：

1. **全异步 Saga**：上下文之间只发命令/事件，每步等待对方事件，流程有等待态、超时、重试与死信；
2. **主流程事件溯源**：聚合不保存当前状态，只追加事件，查询时重放或读投影。

它们都很强大，但会把教学重点从「DDD 战术建模与边界」转移到「分布式一致性与事件存储基础设施」。

## 决定

主流程采用**事件驱动 + 状态存储**：

- 聚合保存当前状态（`Order`、`StockItem`、`Invoice`、`Payment`、`FulfillmentProcess`）；
- 领域事件在聚合内产生，应用层翻译为集成事件写入 Outbox；
- Fulfillment 采用**编排式 Saga**，步骤同步调用其他上下文的应用服务，每步 `REQUIRES_NEW` 提交；
- 补偿是尽力而为的本地事务序列，不是分布式事务；
- **事件溯源只放在 `examples/eventsourcing`**：独立的内存事件存储 + `Account` 聚合 + 重放测试，不接 Spring、不接数据库、不参与主流程；
- 超时按失败处理的简化只适用于演示，真实系统需要「结果未知」状态与对账（见下）。

## 后果

### 好的

- **聚合规则直观**：读者打开 `Order` 就能看到字段、状态机与不变量，不需要先理解事件流、快照、版本、重放。
- **查询简单**：订单详情直接读 `sales_order`，不需要重放事件或维护多层投影。
- **Saga 可控**：同步步骤 + 显式状态机让成功/失败路径容易跟踪；测试只需真实 Spring 上下文 + H2。
- **教学对比清晰**：`examples/eventsourcing` 用很小的代码展示「事件是唯一事实来源」「重放」「流版本乐观锁」，读者可以把它与主流程对照，而不是混在一起。
- **没有事件 schema 演进负担**：主流程的领域事件可以随聚合重构；只有集成事件需要版本意识。
- **故障恢复简单**：当前状态在表里，重启后直接加载；不需要重放全部历史。

### 坏的

- **主流程没有完整审计/重放能力**：只能看到当前状态与 outbox 中的集成事件，不能从领域事件重建任意时刻的聚合。
- **领域事件只用于翻译集成事件**：`OrderLineAdded`/`OrderLineRemoved` 等领域事件没有被持久化，无法做事后分析（除非额外记录）。
- **状态存储与事件可能双写**：应用服务保存聚合后再写 outbox，虽然在同一事务内，但概念上仍是两份数据；需要纪律保证映射正确。
- **无法天然支持「时间旅行」查询**：例如「昨天这个订单的应付金额是多少」需要额外审计表。
- **Saga 仍是同步编排**：Fulfillment 在一个进程内依次调用 Inventory/Billing/Sales；如果某个上下文响应慢，会阻塞 relay 的发布线程。
- **超时语义被简化**：支付超时直接当失败，真实系统可能已扣款成功；缺少「未知结果」与对账。
- **全异步 Saga 的优点没有展示**：没有等待态、超时事件、命令重试、死信队列等生产级模式。

## 替代方案

### 替代方案 A：全异步 Saga

做法：Sales 发布 `OrderPlaced` 后，Fulfillment 发送 `ReserveStock` 命令；Inventory 处理完后发布 `StockReserved`/`StockReservationFailed`；Fulfillment 再发送 `CapturePayment` 命令；每一步都有等待态、超时定时器、重试与死信。补偿也通过命令/事件异步执行。

**不采用的理由：**

- 需要为每个步骤引入等待状态（`AWAITING_STOCK`、`AWAITING_PAYMENT`）、超时事件、重试策略与幂等命令处理；
- 测试必须处理异步时序、超时与重复消息，确定性差；
- 需要消息中间件或至少一个可靠的任务调度器；本项目刻意不引入；
- 读者会把注意力放在分布式工作流基础设施，而不是聚合与边界；
- 当前实现已经能完整展示 Saga、补偿与幂等，异步化不会增加 DDD 教学价值，反而掩盖它。

### 替代方案 B：主流程事件溯源

做法：`Order`、`StockItem`、`Invoice`、`Payment`、`FulfillmentProcess` 都改为事件流；每次命令追加事件，状态由重放得到；查询走投影；聚合版本是流长度。

**不采用的理由：**

- 需要事件存储、快照、流版本、事件升级/迁移、投影重建与一致性处理；
- 领域不变量仍在聚合内，但调试时需要「重放才能看到状态」，对初学者不友好；
- 订单查询、库存查询等读场景需要额外投影，项目复杂度显著上升；
- 集成事件与领域事件的关系会变得更复杂：领域事件成为持久化事实，集成事件是其对外发布形式，版本管理成本更高；
- 本项目已经用 `examples/eventsourcing` 独立展示了事件溯源的核心机制（`Account`、`EventStore`、`InMemoryEventStore`、`AccountEventSourcingTest`），没有必要把它塞进主流程；
- 事件溯源并不自动解决跨上下文一致性；Saga 与 Outbox 仍然需要。

### 替代方案 C：纯 CRUD + 无事件

**不采用的理由：** 无法展示领域事件、Outbox、Saga、CQRS 与上下文协作；订单状态变化会变成「谁最后 update 谁赢」，丢失业务事实。

## 补充：支付超时的真实语义

本项目的 `TimedOut` 被当作失败：

- `Payment(FAILED, reason=TIMEOUT)`；
- `Invoice(VOIDED)`；
- 发布 `billing.payment.failed.v1`；
- Fulfillment 释放库存并取消订单。

真实系统不能这样做。超时意味着「网关可能已扣款，但响应丢失」，需要：

1. 记录「结果未知」状态（而不是直接失败）；
2. 通过网关查询接口或对账文件确认最终结果；
3. 在确认前不释放库存/不取消订单，或使用挂起态；
4. 对重复扣款做退款/冲正；
5. 有超时扫描与人工处理入口。

本项目刻意不实现这些，是为了把 Saga 的成功/失败/补偿讲清楚；这也是 [ADR-0004](0004-outbox.md) 与设计文档中反复强调的「教学简化」。
